## مهم: نوع لوحة التحكم عند النشر على GitHub Pages

**بدون Firebase:** هذه نسخة موقع ثابت صالحة للنشر العام، ويمكن إجراء الحجز **هاتفيًا فقط**. لوحة الإدارة في وضع **التحرير المحلي** ولا تحتاج تسجيل دخول، لأن أي شخص يستطيع تحميل واجهتها الثابتة. لكن تعديلاته لا تنشر شيئًا على الموقع العمومي؛ تبقى في متصفحه فقط. **لا تستقبل النسخة الثابتة بيانات مرضى ولا تحفظ طلبات مواعيد وهمية.**

كيفية نشر التعديلات من لوحة الإدارة في الوضع الثابت:

1. افتح `admin.html` وعدّل النصوص والخدمات والمقالات ومواعيد العمل.
2. من **نظرة عامة** اضغط **معاينة التعديلات** لتراها في نفس المتصفح، دون نشرها للزوار.
3. اضغط **تنزيل بيانات الموقع** لتحصل على `site-data.json`.
4. ارفع **هذا الملف وحده** إلى **جذر مستودع GitHub** لاستبدال النسخة الحالية من `site-data.json`، ثم انتظر إعادة نشر GitHub Pages.
5. بعد اكتمال النشر افتح الموقع عاديًا دون `?preview=1` وتحقق من التغييرات.

يمكنك استيراد نسخة محفوظة من `site-data.json` إلى المحرر. لا تضع في ملف البيانات أي معلومات شخصية تخص المرضى. تعديلات النصوص والدوام التي تغير البيانات المنظمة داخل HTML قد تتطلب تحديث بيانات schema.org أيضًا.

**مع Firebase بعد تفعيله:** يتطلب الدخول بريدًا وكلمة مرور، ويقتصر تعديل المحتوى وإدارة المواعيد على الحسابات المصرح لها عبر قواعد Firestore. التعديلات تنشر لجميع الزوار دون الحاجة لرفع `site-data.json` يدويًا. تتطلب هذه الميزة إعدادًا من صاحب المشروع بحسابه على Firebase، ولا تُفعّل تلقائيًا بمجرد رفع الملفات إلى GitHub.

## خطوات استبدال ملفات الموقع الحالي على GitHub

1. احتفظ بنسخة احتياطية من ملفات المستودع الحالي.
2. فك ضغط الملف المرفق بالمشروع إلى مجلد على الكمبيوتر.
3. افتح المستودع الحالي على GitHub: `azezalal65255-art/dr-munir-clinic.`.
4. ارفع **محتويات المجلد بعد فك الضغط** إلى **جذر المستودع**، وليس ملف ZIP كما هو. احرص أن يكون `index.html` في الجذر، وأن تُحفظ المجلدات `assets`, `css`, `js` كما هي.
5. استبدل ملفات النسخة القديمة بأسماء متشابهة، ويمكن حذف الملفات القديمة غير المستخدمة (`main.js`, `style.css`, `data.js`, `admin.js`) لتجنب الالتباس، بشرط رفع الملفات الجديدة بالكامل أولًا.
6. من **Settings → Pages** تأكد أن مصدر النشر **Deploy from a branch**، والفرع **main**، والمجلد **/(root)**.
7. افتح الرابط الرئيسي والصفحات الداخلية للتأكد، ثم افتح `admin.html` لتجربة المحرر.

إذا كنت تستخدم Git على الكمبيوتر، يمكنك تحديث المستودع بأوامر `git add -A`, `git commit` و`git push` بعد نسخ محتويات مجلد المشروع إلى نسختك المستنسخة من المستودع، مع التأكد من مراجعة التغييرات قبل الدفع.

**ملاحظة بخصوص اسم المستودع:** الاسم الحالي ينتهي بنقطة `dr-munir-clinic.`. لذلك كل الروابط المرفقة هنا تستخدم النقطة حرفيًا. إذا غيّرت اسم المستودع أو ربطت نطاقًا خاصًا، يجب تحديث `canonical` و`sitemap.xml` و`robots.txt`.

## تفعيل قاعدة بيانات ولوحة تحكم حقيقية عبر Firebase (اختياري)

1. افتح https://console.firebase.google.com/ وأنشئ مشروعًا وأضف تطبيق Web.
2. انسخ قيم Firebase الخاصة بتطبيق الويب إلى `js/config.js` (مفاتيح تهيئة الويب عامة، **لكن لا تضع كلمة المرور أو مفاتيح Service Account مطلقًا**).
3. فعّل **Authentication → Email/Password**، وأنشئ حساب المسؤول.
4. فعّل **Cloud Firestore**، والصق قواعد `firestore.rules` في تبويب **Rules** وانشرها. لا تستخدم قواعد تجريبية تسمح للعموم بالقراءة والكتابة.
5. من **Authentication → Users** انسخ UID لحساب المسؤول. داخل Firestore أنشئ collection باسم `admins` ومستندًا document ID يساوي UID، وأضف `active: true` من نوع Boolean. قواعد الأمان لا تسمح لإنشاء هذا الدور من الواجهة العامة.
6. أضف نطاق الموقع `azezalal65255-art.github.io` إلى **Authentication → Settings → Authorized domains** إذا احتجت إليه لإعداد تسجيل الدخول. يكتب النطاق دون مسار المستودع.
7. افتح `admin.html` من الموقع، وسجّل الدخول. إذا لم يُسبق إنشاء البيانات، استخدم زر **تهيئة المحتوى الافتراضي**.
8. اختبر من حساب عادي غير مسؤول أنه لا يستطيع عرض الحجوزات أو تعديل المحتوى. اختبر أيضًا نموذج الموعد مع بيانات **تجريبية غير حقيقية** قبل تفعيله للعامة.

### رفع الصور من لوحة الإدارة (اختياري)

يمكن استخدام رابط صورة آمن (HTTPS) دون الحاجة إلى Storage. لرفع ملفات الصور مباشرة، فعّل Cloud Storage، وانشر `storage.rules` وفق إعدادات مشروعك. قد يتطلب تفعيل Storage خطة فوترة Blaze، وتختلف حدود الاستهلاك والتكلفة. لا ترفع صور مرضى أو تقارير شخصية للمعرض العام.

### تنبيه حماية إضافي للحجز الإلكتروني

قواعد Firestore المرفقة تقصر قراءة الطلبات على المسؤول وتتحقق من نوع الحقول، لكنها **لا تمنع وحدها الرسائل الآلية أو إساءة الاستخدام**. قبل جمع بيانات مرضى حقيقية، أضف طبقة للحد من الإرسال المتكرر (مثل App Check أو خدمة backend تتحقق من الطلبات)، وحدد سياسة الاحتفاظ بالبيانات، وراجع سياسة الخصوصية والإجراءات المناسبة لحماية معلومات المرضى.

## التشغيل والفحص المحلي

من مجلد المشروع:

```bash
python -m http.server 8080
```

ثم افتح `http://localhost:8080/`. ولا تفتح الملفات مباشرة بـ `file://`؛ لأن JavaScript Modules وطلب `site-data.json` يحتاجان خادم ويب.

لإجراء اختبار المنطق المحلي إذا كان Node.js متاحًا:

```bash
npm test
```

## ملفات المشروع الأساسية

- `index.html` — الرئيسية.
- `admin.html` — لوحة إدارة المحتوى.
- `js/site.js` — واجهة الزوار.
- `js/admin.js` — وظائف لوحة الإدارة.
- `js/store.js` — طبقة البيانات (ملف منشور أو Firebase).
- `site-data.json` — البيانات العامة التي يقرأها الزوار في الوضع الثابت.
- `js/config.js` — إعدادات ربط Firebase الاختيارية.
- `firestore.rules` و`storage.rules` — قوالب قواعد الأمان للنسخة المتصلة.
- `robots.txt`, `sitemap.xml`, `.nojekyll` — ملفات GitHub Pages ومحركات البحث.

هذه الملفات جاهزة للرفع. **لا يمكن لهذا الملف وحده إجراء Push إلى حساب GitHub؛ لا يصبح الموقع العام محدّثًا إلا بعد رفع الملفات إلى المستودع.**
